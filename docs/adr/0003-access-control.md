# ADR-0003. Контроль доступа: регистрация пользователей с одобрением администратором

- **Статус:** Accepted (PM подтвердил решения, § 10)
- **Дата:** 2026-10-13
- **Автор:** software-architect
- **Задача:** [`docs/tasks/access-control.md`](../tasks/access-control.md) (закрывает уязвимость H2 аудита)
- **Затрагивает:** `cmd/bot/bot.go`, `cmd/bot/main.go` (новые `cmd/bot/access.go`, `cmd/bot/callbacks.go`),
  `internal/config` (без изменения API), `docker-compose.yml`, `.env.example`, схема SQLite (новая таблица `users`)
- **Связанные находки аудита:** H1 (падение бота на не-`message` обновлениях) — исправляется в рамках этого решения, см. § 1.3

---

## 1. Контекст

### 1.1. Угроза H2

В боте полностью отсутствует авторизация: любой пользователь Telegram, знающий
username бота, выполняет `/start` → `/author` → `/get N` и выгружает всю
библиотеку оператора. Диспетчеризация в `cmd/bot/bot.go` проверяет только текст
команды (`actions`-мапа), личность отправителя не проверяется нигде.

### 1.2. Текущее состояние кода (факты, на которые опирается решение)

1. `processNotifications` (`cmd/bot/bot.go:56–78`) единственная точка входа всех
   обновлений; уже в первой строке (`:60`) безусловно разыменовывает
   `update.Message`.
2. Состояние поиска — per-user в памяти (`Searcher`, `cmd/bot/searcher.go`),
   теряется на рестарте; к контролю доступа отношения не имеет.
3. Схема БД создаётся `cmd/db-create` (`CREATE TABLE IF NOT EXISTS books ...`);
   механизма версионированных миграций нет. Бот открывает базу точкой
   `DB_DSN` и ранее только читал `books`.
4. `internal/config` читает всё из ENV; `config.Required(...)` собирает **все**
   отсутствующие обязательные переменные в одно сообщение и приводит к
   `exit 1` — паттерн fail-fast, который требует FR7.
5. В `docker-compose.yml` каталог базы `/data` примонтирован боту **на запись**
   (без флага `read_only` у volume), контейнер бота работает под `uid/gid 10001`
   (`USER app:app` в Dockerfile). То есть физическая возможность писать в базу
   у бота уже есть; меняются только требования к правам на хосте (см. § 4.6).

### 1.3. Находка H1 и её связь с задачей (обязательный контекст)

Бот использует `github.com/go-telegram-bot-api/telegram-bot-api v4.6.4`.
В этой версии у `UpdateConfig` **нет поля `AllowedUpdates`** — запрос `getUpdates`
уходит без параметра `allowed_updates`, и Telegram по умолчанию доставляет все
типы обновлений, кроме `chat_member`. Это значит:

- `callback_query`, `edited_message` и прочие не-`message` обновления **уже
  сегодня** попадают в `processNotifications` и обрушивают бот panic'ом на
  `update.Message.Chat.ID` (H1). Recovery в контейнере (`restart: on-failure:5`)
  лишь маскирует проблему и при каждом падении теряет in-memory состояние поиска
  всех пользователей.
- Новый функционал (inline-кнопки регистрации и решения администратора) делает
  `callback_query` штатным типовым обновлением. Следовательно, **исправление H1
  является предпосылкой фичи и входит в объём этого решения**, а не отдельной
  задачи: фича без него неработоспособна по определению.

Фикс H1 в рамках задачи — не whitelist (его в v4.6.4 выразить нечем), а
nil-safe роутинг по типам обновлений + `recover()` на обработку каждого
апдейта (§ 4.3).

## 2. Драйверы решения

| # | Драйвер | Источник |
|---|---|---|
| D1 | Закрыть H2: ни один неодобренный пользователь не должен достичь `repository.Search` / `storage.GetFile` | FR1 |
| D2 | Ровно одна активная заявка на пользователя; blacklist без повторной заявки | FR2, сценарий 5 |
| D3 | Статус — по БД на каждом запросе, переживает рестарт | FR5, FR6 |
| D4 | Решение администратора — только двумя inline-кнопками на сообщении заявки | FR4 |
| D5 | Обязательная ENV-переменная с Telegram ID администратора, fail-fast единым сообщением | FR7, паттерн `internal/config` |
| D6 | Поведение одобренного пользователя не меняется: `/start`, `/author`, `/title`, `/result`, `/get` — как раньше | требование задачи п.4 |
| D7 | Бот не должен падать на не-`message` обновлениях; `callback_query` становится штатным | H1 |
| D8 | Минимальный стек: без новых зависимостей, без миграционных фреймворков, без новой БД | KISS/YAGNI, AGENTS.md |
| D9 | Единая точка проверки доступа — её нельзя «обойти» новым кодом | safe by construction |

## 3. Рассмотренные варианты

### Вариант A: таблица `users` в существующем SQLite + guard в роутере обновлений + inline-кнопки

**Описание:** состояние пользователя (`pending`/`approved`/`declined`) хранится в
новой таблице `users` той же базы. Перед диспетчеризацией команд встаёт чистая
функция-страж (`AccessGuard`), сверяющая `From.ID` с БД. Кнопки — inline
(`InlineKeyboardMarkup`), решения администратора — callback'и с целевым ID.

**Плюсы:**
- FR3/FR5/FR6 выполняются «всего лишь» одной таблицей; запрос `SELECT status …`
  по локальному SQLite — микросекунды, кэши не нужны.
- Никаких новых зависимостей, тома и монтирование уже настроены (D8).
- Guard — одна ворота для всех message-обновлений: новый код не может забыть
  проверку, если он добавлен в `actions` (D9).
- Идемпотентность решения администратора выразима одним атомарным
  `UPDATE … WHERE status='pending'`.

**Минусы:**
- Бот становится писателем в базу: требования к правам на `DATA_HOST_DIR`
  ужесточаются (снимается в § 4.6).

**Оценка:** ✅ Выбран

---

### Вариант B: хранение пользователей в YAML/JSON-файле рядом с базой

**Плюсы:** не трогает схему.

**Минусы:** нарушает FR5 аккуратнее, чем кажется (атомарная перезапись,
отсутствие CHECK-ограничений, дублирование инфраструктуры персистентности);
оператор уже работает с базой через sqlite3; два источника истины.

**Оценка:** ❌ Отклонён

---

### Вариант C: заявки только в памяти, одобрение текстовыми командами администратора (`/approve N`)

**Плюсы:** почти нулевая реализация.

**Минусы:** нарушает FR4 (только кнопки) и FR5 (pending переживает рестарт, а
одобренные — куда? тоже память → падает FR5 целиком).

**Оценка:** ❌ Отклонён

---

### Вариант D: фреймворк миграций (goose / golang-migrate / PRAGMA user_version)

**Плюсы:** дисциплина схемы на будущее.

**Минусы:** одна аддитивная таблица без изменения `books` — единственный
известный сценарий; фреймворк добавляет зависимость и build-шаг ради `CREATE
TABLE IF NOT EXISTS`. В проекте уже есть прецедент само-идемпотентного создания
схемы (`db-create`).

**Оценка:** ❌ Отклонён как избыточный; «люк» для будущего — `PRAGMA user_version`
(§ 4.6), внедряется только при первом неаддитивном изменении.

---

### Вариант E: апгрейд `telegram-bot-api` до v5 (+ whitelist `AllowedUpdates`)

**Плюсы:** поддерживаемая ветка библиотеки; whitelist сделал бы поверхность
обновлений явной.

**Минусы:** ломающий апгрейд API по всему `cmd/bot` вне рамок задачи; whitelist
не отменяет необходимости nil-safe роутинга и recover (edited_message всё равно
разрешён, а `message` без `from` существует). В v4.6.4 callback'и доставляются и
так — фиче апгрейд не нужен.

**Оценка:** ❌ Отклонён (кандидат в отдельный технический долг, не блок этой задачи)

---

### Вариант F: кэш одобренных ID в памяти процесса

**Плюсы:** убирает запрос к SQLite на сообщение.

**Минусы:** FR6 требует решение по БД на каждом запросе; инвалидация кэша —
источник багов; масштаб «личная библиотека, один процесс» не создаёт нагрузки,
ради которой кэш нужен.

**Оценка:** ❌ Отклонён (преждевременная оптимизация, риск рассинхрона)

## 4. Выбранное решение

### 4.1. Хранение: таблица `users` в существующей базе

```sql
CREATE TABLE IF NOT EXISTS users (
    telegram_id   INTEGER PRIMARY KEY,              -- ID Telegram; он же ключ заявки (FR2)
    status        TEXT NOT NULL
                  CHECK (status IN ('pending','approved','declined')),
    first_name    TEXT NOT NULL DEFAULT '',         -- снимок из Telegram на момент заявки (FR3)
    last_name     TEXT NOT NULL DEFAULT '',         -- '' если Telegram не отдал поле
    username      TEXT NOT NULL DEFAULT '',         -- без '@', как отдаёт Telegram
    language_code TEXT NOT NULL DEFAULT '',
    created_at    TEXT NOT NULL,                    -- RFC3339 UTC, момент заявки
    decided_at    TEXT                              -- RFC3339 UTC; NULL пока заявка активна
);
```

Обоснования:

- **PK = `telegram_id`, без AUTOINCREMENT.** Пользователь физически не может
  иметь больше одной строки, а значит и больше одной активной заявки — FR2
  обеспечивается схемой, а не кодом.
- **Статус — TEXT с `CHECK`.** В SQLite `CHECK` на TEXT самодокументируем для
  оператора (`sqlite3 db 'SELECT * FROM users'`) и дешевле по времени, чем
  магия чисел. Три значения точно соответствуют трём статусам задачи;
  «отзыв доступа» и «разбан» в схему не закладываются (вне рамок, YAGNI).
- **Снимок профиля (`first_name`…`language_code`)** пишется один раз из
  `CallbackQuery.From` в момент заявки: к моменту решения администратор должен
  видеть ровно те данные, на основании которых принимал решение (FR3). При
  отсутствии фамилии/username в заявке отображается только то, что отдал
  Telegram (edge case задачи) — пустые поля не печатаются.
   - **Администратор строки в `users` не имеет** (см. § 4.3, правило M3): он
  не может ни зарегистрироваться, ни попасть в blacklist — edge case задачи
  выполняется отсутствием данных, а не проверками.
- Таблица **не** попадает в пакет `storage` (там общий row-модель `books` для
  пайплайна и бота): `users` — приватная схема бота, `scan`/`db-create` её не
  читают и не создают. `books` не меняется.

**Машина состояний:**

```
            req:new              adm:approve
 (нет строки) ────> pending ────────────────────> approved   (терминальное)
                   pending ──── adm:decline ────> declined   (терминальное)
 (нет перехода declined → *, approved → * — разбан и отзыв вне рамок)
```

Все переходы — только из `pending`, атомарно (§ 4.4).

### 4.2. Конфигурация: `ADMIN_TELEGRAM_ID`

- Имя: **`ADMIN_TELEGRAM_ID`** — значение «Telegram ID», имя не оставляет
  свободы интерпретации (chat ID vs user ID для личных сообщений совпадают,
  но имя фиксирует намерение).
- Обязательная: добавляется в `config.Required("BOT_TOKEN", "LIBRARY_DIR",
  "DB_DSN", "ADMIN_TELEGRAM_ID")` в `cmd/bot/main.go` — отсутствующая
  переменная попадает в единое сообщение `missing required environment
  variables: …`, exit 1 (FR7; тот же UC5-контракт, что проверяет
  `main_test.go`).
- Валидация значения: `strconv.ParseInt` в `cmd/bot/main.go` сразу после
  `Required`; нечисловое/отрицательное/нулевое значение — `configuration:
  ADMIN_TELEGRAM_ID must be a positive integer, got "…"`, exit 1. Новый API в
  `internal/config` не вводится (KISS: нужен один раз в одном месте;
  типизация чужих переменных — не задача config-пакета).
- `LegacyEnv` не пополняется: у новой переменной нет предшественницы.
- `.env.example`: переменная добавляется в секцию «обязательные» с комментарием,
  где взять ID (написать, например, `@userinfobot`).
- `docker-compose.yml`: в `bot.environment` — `ADMIN_TELEGRAM_ID: "${ADMIN_TELEGRAM_ID:-}"`.
  Пустое значение намеренно проходит compose «как есть»: единственная точка
  валидации — приложение (тот же принцип, что у `BOT_TOKEN`, ADR-0001 § 5.6).
- Только `bot` получает переменную; `scan`/`db-create` — нет (им не нужен).

### 4.3. Конвейер обработки апдейтов: роутер + guard (фикс H1 встроен)

`processNotifications` переписывается в роутер; каждый апдейт обрабатывается
под `defer recover()`:

```
for update := range updatesChan:
    ├─ R0: defer recover() per update → slog.Error("panic while handling update",
    │      "update_id", …, "err", …); бот продолжает работать (H1)
    ├─ R1: update.CallbackQuery != nil            → handleCallback (§ 4.4)
    ├─ R2: update.Message != nil                  → message-ветка (§ ниже)
    └─ R3: иначе (edited_message, channel_post, …) → slog.Debug + ignore
```

Правила message-ветки (порядок фиксирован):

| # | Правило | Обоснование |
|---|---|---|
| M1 | `update.Message.From == nil` → ignore + slog.Warn | защита от nil; channel-артефакты |
| M2 | `!update.Message.Chat.IsPrivate()` → ignore + slog.Debug | допущение задачи: бот работает только в личных сообщениях; группа не должна уметь ни скачивать, ни регистроваться |
| M3 | `From.ID == adminID` → **Allow**, в БД не смотрим | админ не проходит регистрацию (§ 4.1); админа нельзя забанить данными |
| M4 | иначе `status := accessRepo.Status(From.ID)` (запрос к БД на каждое сообщение) | FR6 буквально |
| M5 | `approved` → существующая диспетчеризация `actions` — **без изменений** | требование «не менять поведение одобренного» (D6) |
| M6 | нет строки → текст-«закрыто» + inline-кнопка «Зарегистрироваться» | сценарий 1 |
| M7 | `pending` → текст «заявка на рассмотрении» (без кнопки) | сценарий 3 |
| M8 | `declined` → текст «доступ отказан» (без кнопки) | сценарий 5 |

- Статус-ответы (M6–M8) собираются новым хелпером **без** `replyKeyboard`
  (клавиатура с `/start` неодобренному бесполезна и вводит в заблуждение);
  `createTextReplyMessage` для одобренных не трогается.
- Guard стоит **до** разбора команды и до `repository`/`storage`: путь к данным
  библиотеки физически отсутствует для всех статусов, кроме `approved` (D9).
  Никакая новая команда в `actions` не может «протечь» мимо стража.
- In-memory `Searcher` не меняется: неодобренный пользователь не имеет состояния
  поиска, одобренный — ведёт себя как раньше.

### 4.4. Callback-протокол и решение администратора

Callback data (лимит Telegram 1–64 байта, формат стабильный — он «зашит» в
истории чатов и переживает рестарты):

| Data | Кто может нажать | Действие |
|---|---|---|
| `req:new` | любой, кроме админа | создать `pending`-строку, доставить заявку админу |
| `adm:approve:<telegram_id>` | только `adminID` | переход `pending → approved` |
| `adm:decline:<telegram_id>` | только `adminID` | переход `pending → declined` |

Правила безопасности и идемпотентности:

- **C1. Авторизация решения.** Первая проверка в обработчике
  `adm:*`: `CallbackQuery.From.ID == adminID`; иначе —
  `AnswerCallbackQuery` с alert «You are not allowed to decide», БД не
  трогается. Кнопка в чужом chat — не привилегия.
- **C2. `req:new` не несёт целевой ID** — действие всегда применяется к
  `From.ID`. Это закрывает атаку «переслал чужу кнопку регистрации —
  зарегистрировал жертву»: нажатие регистрирует нажавшего, данными
  нажавшего (`From`), что безопасно по построению.
- **C3. Атомарный переход:**
  `UPDATE users SET status=?, decided_at=? WHERE telegram_id=? AND status='pending'`.
  `RowsAffected == 0` → повторный `SELECT status` и alert администратору:
  - `approved` + approve → «user is already approved» (идемпотентно, edge case задачи);
  - `approved` + decline → «access revocation is out of scope» (без изменений);
  - `declined` + любой → «user has already been declined» (без изменений);
  - `pending` теоретически возможен при гонке — повторить переход; в одном
    обработчике-горутине обновлений гонки нет, эту ветку оставляем
    защитно-логирующей.
- **C4. Погашение сообщения заявки.** После успешного перехода —
  `EditMessageText`: текст с итогом («Request accepted: …»), клавиатура снимается
  пустым `InlineKeyboardMarkup`. Если edit не удалось (сеть) — не беда:
  состояние в БД, повторное нажатие перехватывается C3.
- **C5. Каждой callback отвечает** `AnswerCallbackQuery` (обычный ответ —
  пользователю, alert — администратору в спорных случаях), иначе Telegram
  крутит «часы» до таймаута.
- **C6. Регистрация из `pending`:** «Зарегистрироваться» повторно →
  строка не создаётся (PK + `INSERT … ON CONFLICT(telegram_id) DO NOTHING`),
  пользователю alert «request already sent». Дополнительно заявка
  **переотправляется админу** — это лечит случай «доставка первой заявки
  упала» (см. C7) без дублей решения: решение привязано к `telegram_id`, а не
  к message_id админа, поэтому лишние копии заявки админу безвредны —
  «выигравшая» кнопка решает, остальные гасятся C3/C4.
  Уточнение (реализация T-23): `declined`/`approved` тап по старой кнопке
  `req:new` отсекается **до** пересылки (alert «declined» / «already
  approved») — blacklist-пользователь не создаёт админу новых заявок вообще.
- **C7. Доставка заявки админу** — `bot.Send` в чат `adminID`. Предположение:
  админ хотя бы раз написал боту (Telegram не позволяет боту писать первым).
  Ошибка доставки — `slog.Error` + alert пользователю «failed to notify the
  admin, try again»; заявка остаётся `pending` и будет переотправлена (C6).
  Требование «бот запущен, админ написал» фиксируется в README (шаг приёмки).
- **C8. `req:new` от админа** → alert «Admin does not need registration»,
  строка не создаётся (edge case задачи).
- **C9. `adm:*` на `telegram_id == adminID`** (вручную подделанный callback —
  теоретически недостижим из UI) → alert «The admin cannot be blacklisted».
- **C10. Неизвестный callback data** → alert «Action not supported», slog.Warn.

**Уведомление пользователя о решении** (architectural decision: в объёме):
после успешного перехода бот отправляет одобренному «Your access has been
approved…», отклонённому — «Your registration request was declined.». Если
пользователь заблокировал бота — `slog.Warn`, решение не откатывается
(истина в БД; пользователь узнает статус при следующем обращении). Без
уведомления пользователю пришлось бы «тыкать» бота, чтобы узнать результат, —
минимальное UX-дополнение, не расширяющее поверхность безопасности.

**Текст заявки администратору** (только непустые поля):

```
New registration request
ID: 123456789
Name: Ivan
Last name: Petrov        <- отсутствует, если Telegram не отдал
Username: @ivan          <- отсутствует, если Telegram не отдал
Language: ru             <- отсутствует, если Telegram не отдал
[ Принять ] [ Отклонить ]   (inline: adm:approve:123456789 / adm:decline:123456789)
```

Язык пользовательских строк — английский, как существующие строки бота
(`Command not supported`); см. открытый вопрос Q3.

### 4.5. Создание схемы и «миграция»

- Схему `users` создаёт **сам бот** при старте: `AccessRepository.EnsureSchema()`
  — `CREATE TABLE IF NOT EXISTS …`, вызывается в `run()` сразу после успешного
  `db.Ping()`, до `newBot`. Ошибка создания — `return fmt.Errorf("init users
  schema: %w", err)` → exit 1 (fail-fast, консистентно с остальными стартовыми
  проверками).
- Почему не `cmd/db-create`: это одноразовый индексатор библиотеки, жёстко
  связанный с сайдкарами; требовать его повторного прогона как шаг апгрейда
  бота — лишать деплой атомарности (забыл/не смог → бот лежит). Само-идемпотентная
  схема на старте — уже принятый в проекте паттерн (так `db-create` создаёт
  `books`), и порядок «бот/`db-create` что раньше» перестаёт иметь значение:
  свежая база, созданная `db-create`, получает `users` при первом старте бота;
  база с `users` не мешает `db-create`.
- **Миграция данных не требуется**: таблица аддитивна, `books` не меняется.
  Подъём старой базы — просто первый запуск новой сборки бота.
- Люк на будущее: при первом **неаддитивном** изменении схемы — внедрить
  `PRAGMA user_version` + версионированные шаги в одном месте (тогда и
  обсуждается goose). Сейчас — YAGNI.

### 4.6. Последствия для развёртывания: бот становится писателем БД

Ранее бот к базе фактически только обращался на чтение. Теперь он:
создаёт таблицу, `INSERT`'ит заявки, `UPDATE`'ит решения. Следствия:

1. compose-монтирование `/data` уже RW — конфигурация тома не меняется;
2. но каталог `DATA_HOST_DIR` на хосте должен быть **записываем для uid 10001**
   (владелец уже обеспечивается шагом `chown` в README для `db-create` —
   требование становится обязательным, а не «нужным только при индексации»);
3. в README добавляется раздел контроля доступа и это требование (план T-23).

### 4.7. Поведение при рестарте

- Статусы (`approved`/`declined`/`pending`) — в SQLite, переживают рестарт (FR5).
- Сообщения заявок в чате администратора — «внешнее хранилище»: callback data
  живёт в истории Telegram, а решение опирается на `telegram_id` + состояние БД,
  поэтому **кнопки старых заявок работают после рестарта**; устаревшие
  обработаны C3/C4.
- Никакого нового in-memory состояния контроль доступа не вводит (guard
  stateless, только запрос к БД) — рестарт не может рассинхронизировать память
  и базу.
- In-memory состояние поиска терялось и раньше — поведение не меняется.

### 4.8. Размещение кода

| Файл | Содержание |
|---|---|
| `cmd/bot/access.go` (новый) | `AccessStatus` (enum + строковые значения), `AccessRepository` (`EnsureSchema`, `Status`, `CreatePending`, `Decide`), `AccessGuard` (чистая функция M3–M8 над репозиторием) |
| `cmd/bot/callbacks.go` (новый) | константы callback data, парсер `adm:*`, обработчики `req:new` / `adm:*` (C1–C10), текст заявки |
| `cmd/bot/bot.go` | роутер `processNotifications` (R0–R3), вызов guard'а, `Bot` получает поля `access *AccessRepository`, `adminID int64` |
| `cmd/bot/main.go` | `ADMIN_TELEGRAM_ID` в `Required` + парсинг, `EnsureSchema()` после `Ping`, проводка в `newBot` |
| `internal/config` | без изменений API |
| `docker-compose.yml`, `.env.example` | новая переменная (только в `bot`) |

Всё — в `package main` бота, по прецеденту `repository.go`: логика доступа нужна

Ядро (`AccessGuard`, парсер callback data, переходы) — чистые функции/методы,
тестируемые без Telegram.

## 5. Влияние на существующее поведение

| Сценарий | До | После |
|---|---|---|
| Одобренный (или админ): `/start /author /title /result /get` | работает | **работает без изменений** (тексты, клавиатура, поиск, выдача файла) |
| Неизвестный пишет боту | получает команды/результаты (H2) | «доступ закрыт» + кнопка «Зарегистрироваться» |
| Pending пишет боту | работает (H2) | «заявка на рассмотрении» |
| Declined пишет боту | работает (H2) | «доступ отказан» |
| `edited_message` / любое не-`message` | **panic**, рестарт контейнера | обработано/проигнорировано, бот жив (H1) |
| `callback_query` | panic | штатная обработка |
| Сообщение в группе/канале | panic или утечка через `From`-nil | игнор (явное допущение) |
| Незарегистрированный жмёт `adm:*` | n/a | alert «not allowed», без изменений БД |
| Кнопка на уже решённой заявке | n/a | понятный alert, БД не меняется |
| `/get` без `/start` (одобренный) | «start search first» | без изменений |

## 6. Стратегия тестирования

1. **`cmd/bot/access_test.go`** (SQLite `:memory:`, precedent: `main_test.go` уже
   использует mattn/go-sqlite3): EnsureSchema идемпотентен; CreatePending
   UNIQUE-конфликт (`ON CONFLICT DO NOTHING`, RowsAffected); Decide из pending —
   успех, из terminal — RowsAffected 0; переходов `approved→*`, `declined→*` нет.
2. **Guard — табличные unit-тесты** (чистая функция, без сети): админ → allow
   независимо от строки в БД; unknown/pending/declined/approved × (message) →
   ожидаемый исход; nil-From; не-private chat.
3. **Роутер — табличные unit-тесты**: `Update`-структуры (message only,
   callback only, edited_message, пустой update) → ожидаемая ветка; panic в
   обработчике не убивает цикл (R0).
4. **Парсер callback data**: `adm:approve:<id>`, мусор, превышение, свой/чужой
   ID.
5. **Конфигурация**: `main_test.go` — обновить ожидаемое сообщение missing
   (добавить `ADMIN_TELEGRAM_ID`); новый тест «нечисловой ID → внятная ошибка».
6. **Ручная приёмка** UC по критериям задачи (план T-23), включая перезапуск
   бота между заявкой и решением.

Интеграционные тесты с реальным Telegram не вводятся (нет инфраструктуры;
соответствует текущему уровню проекта).

## 7. Соображения безопасности (довод закрытия H2)

- Единственные врата к `repository.Search` и `storage.GetFile` — диспетчер
  `actions` из message-ветки, которая начинается guard'ом (D9). Иных путей
  вызова этих методов в бинаре `bot` нет.
- `AnswerCallbackQuery`/`EditMessageText` не возвращают данных библиотеки.
- Подделка «решения» невозможна без `From.ID == adminID` (C1); identity
  отправителя даёт Telegram-транспорт.
- Регистрация по кнопке не принимает входных данных от пользователя помимо
  самого факта нажатия; снимок профиля берётся из доверенного `From`.
- Хранение PII (имя/фамилия/username/язык) в базе оператора — принято:
  минимально необходимое для FR3; flow удаления вне рамок задачи (риск RR5).
- ID администратора — не секрет (он осмыслен только в связке bot↔Telegram
  callback); тем не менее `.env` в git не попадает (существующая практика).

## 9. Соответствие требованиям

| FR | Механизм |
|---|---|
| FR1 | Guard M5–M8 до диспетчера; у не-approved нет пути к search/storage |
| FR2 | PK `telegram_id` + `ON CONFLICT DO NOTHING` + ветка pending (C6) |
| FR3 | Снимок `From` в `users`; заявка показывает непустые поля |
| FR4 | Только `adm:approve`/`adm:decline` inline-кнопки; текстовых админ-команд нет |
| FR5 | Таблица `users` в SQLite; guard stateless |
| FR6 | M4: `SELECT status …` на каждое сообщение |
| FR7 | `ADMIN_TELEGRAM_ID` в `config.Required` → единое сообщение, exit 1 |

Критерии приёмки задачи покрываются планом T-18…T-23; ручная приёмка — T-23.
