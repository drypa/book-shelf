# T-08. Скрипты `common.sh`, `build.sh`, `up.sh`, `scan.sh`, `db-create.sh`

- **Приоритет:** P0
- **Оценка:** 0.5 дня
- **Зависит от:** T-07
- **Блокирует:** T-10, T-11, T-12
- **Основание:** ADR-0001 §5.5

---

## Цель

Дать оператору четыре команды вместо ручной работы с `docker compose`, без
установки чего-либо на хост и без сборки Go на хосте.

## Контекст

Требования FR5: скрипты запускаются из корня репозитория, читают `.env` сами (через
compose), не требуют ручных переменных окружения и не собирают бинарии Go на хосте.
Содержимое скриптов зафиксировано в ADR §5.5 — реализовать **ровно его**, с двумя
предостережениями, вытекающими из проверок:

- `docker compose build` без `--profile` **не собирает** `scan` и `db-create` (ADR §4, E3);
- `docker compose run` на профильном сервисе работает **без** указания `--profile` (E5),
  а код возврата контейнера пробрасывается точно (E6) — значит, `scan.sh`/`db-create.sh`
  сводятся к одной команде.

## Что делать

1. Создать `scripts/common.sh` с тремя функциями (`compose`, `require_env_file`,
   `preflight`) по спецификации ADR §5.5. Обоснование вынесения в отдельный файл: одна и
   та же проверка нужна в четырёх скриптах, а правило «`config -q`, потому что `config`
   напечатал бы токен» должно быть единым, а не продублированным с расхождениями.

2. Создать `build.sh`, `up.sh`, `scan.sh`, `db-create.sh` по спецификации ADR §5.5:

   | Скрипт | Команда | Особое |
   |---|---|---|
   | `build.sh` | `compose --profile "$COMPOSE_PROFILES" build` | `--profile` обязателен (E3); комментарий в коде |
   | `up.sh` | `compose up -d` | буквально «только `up -d`» + `preflight` + подсказки |
   | `scan.sh` | `compose --profile "$COMPOSE_PROFILES" run --rm --no-deps -T scan` | код возврата пробрасывается (E6) |
   | `db-create.sh` | `compose --profile "$COMPOSE_PROFILES" run --rm --no-deps -T db-create` | предупреждение о дублях в тексте скрипта |

   Во всех: `set -euo pipefail`, `cd "$(dirname "${BASH_SOURCE[0]}")"`,
   `. ./scripts/common.sh`, `preflight`, полезный `echo` в конце.

3. Объяснение `-T` дать комментарием в `scan.sh`/`db-create.sh`: без него вывод может
   получить псевдо-TTY-обёртку и стать непригодным для последующего разбора. Флаг
   `--no-deps` — страховка на случай будущего `depends_on` (ADR §6, R4).

4. **Не** читать `.env` в скриптах (`source .env` запрещён — ADR §6, R6). Аргументы
   `scan` и `db-create` заданы в `command` сервисов compose.

5. Сделать все пять файлов исполняемыми: `chmod +x build.sh up.sh scan.sh db-create.sh`.

## Критерии приёмки

- [ ] `./build.sh` завершается кодом 0 и создаёт три образа
      (`docker images | grep book-shelf`).
- [ ] `./up.sh` поднимает только бота; `docker compose ps` показывает одну строку `running`.
- [ ] `./scan.sh` отрабатывает до завершения и возвращает код контейнера; при подставленном
      несуществующем каталоге — ненулевой код.
- [ ] `./db-create.sh` возвращает код контейнера.
- [ ] Ни один скрипт не требует предустановленных переменных окружения в shell: запуск
      через `env -i PATH=… bash ./up.sh` не падает на отсутствии `.env` переменных в
      окружении процесса.
- [ ] При отсутствии `.env` каждый скрипт печатает понятное сообщение
      `cp .env.example .env` и завершается с ненулевым кодом.
- [ ] `BOT_TOKEN` не печатается ни одним скриптом (используется только `config -q`).
- [ ] `shellcheck build.sh up.sh scan.sh db-create.sh scripts/common.sh` — без замечаний
      (либо с обоснованными `# shellcheck disable`).
- [ ] Скрипты не содержат `source`, `go build`, `go run`.

## Риски и примечания

- Если оператор скопирует `build.sh` отдельно от `scripts/common.sh`, скрипт упадёт с
  невнятной ошибкой. Добавить в `common.sh` проверку существования `docker-compose.yml` и
  вывести понятное сообщение «запускайте из корня репозитория».
- `set -e` в `scan.sh` означает, что при ненулевом коде контейнера финальный `echo`
  не напечатается — это правильное поведение, но в README (T-10) нужно показать, что
  выглядит как «ошибка в логах выше».
