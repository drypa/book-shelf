# T-15. Расширение CI: `go vet`, `go build ./...`, сборка образа

- **Приоритет:** P2
- **Оценка:** 0.5 дня
- **Зависит от:** T-06
- **Блокирует:** —
- **Основание:** ADR-0001 §11 (критерии 16, 17)

---

## Цель

Закрепить в CI то, что обязательно по критериям приёмки, чтобы регрессии ловились
автоматически, а не при ручной проверке.

## Контекст

Текущий `.github/workflows/go.yml` выполняет ровно одну проверку:

```yaml
- name: Build Bot
  run: go build -v ./cmd/bot/...
```

Из этого следуют две проблемы:

1. **`go build ./...` не проверяется** — бинари `scan` и `db-create` могут перестать
   собираться незаметно (что уже случалось: `go vet` падал на `cmd/bot`, а CI был зелёным).
2. **cgo в CI не проверяется.** Сборка `bot` проходит, но `go vet` по всему
   репозиторию, требующий разрешения зависимостей sqlite3, может вести себя иначе.

## Что делать

1. Расширить существующий job `build` (не плодить параллельные job без нужды):

   ```yaml
   jobs:
     build:
       runs-on: ubuntu-latest
       steps:
       - uses: actions/checkout@v4
       - uses: actions/setup-go@v5
         with:
           go-version: '1.24'
       - name: gofmt
         run: test -z "$(gofmt -l .)"
       - name: Build all binaries
         run: go build -v ./...
       - name: Vet
         run: go vet ./...
       - name: Test
         run: go test ./archive/... ./finder/... ./storage/... ./internal/...
   ```

   `setup-go@v4` → `v5` — обновление, оправданное: v4 на устаревших раннерах уже
   deprecated.

2. Отдельно решить, включать ли `go test ./...`: он падает на `format/fb2` до
   завершения T-14. После T-14 — включать целиком. До него — явный список пакетов,
   сопровождаемый `TODO(T-14)`, чтобы ограничение было заметным.

3. Добавить **опциональный** шаг проверки сборки образов (job `docker`, или шаг с
   `if: github.event_name == 'push'`):

   ```yaml
   - name: Build images
     run: docker compose --profile tools build
   ```

   Важно: именно `--profile tools` — без него соберётся только `bot` (ADR §4, E3).
   Шаг «долгий» (сборка cgo-образов), поэтому либо вынести в отдельный job, либо
   ограничить ветками.

4. Не добавлять в CI шаги, требующие секретов: `BOT_TOKEN` в CI не нужен и не должен
   там появляться (NFR: секреты не в образах и не в git).

## Критерии приёмки

- [ ] CI зелёный на текущем HEAD **после** T-03…T-05.
- [ ] CI падает, если в `cmd/scan` или `cmd/db-create` внесена ошибка сборки.
- [ ] CI падает на `slog.Error("…", err)`-подобном нарушении vet.
- [ ] При `docker compose --profile tools build` в CI собираются три образа; при
      сборке без `--profile` — один (это можно зафиксировать как ожидаемое поведение
      комментарием, а не как проверку).
- [ ] В workflow нет ни одного секрета.

## Риски и примечания

- Если T-14 не выполнен, `go test ./...` в CI будет красным — не «чинить» это
  ослаблением шага, а либо выполнить T-14, либо явно перечислить пакеты.
- Сборка образов в CI заметно медленнее Go-сборки; взвесить необходимость против
  времени пайплайна (это обоснование статуса P2).
