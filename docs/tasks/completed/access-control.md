# Контроль доступа к библиотеке: регистрация пользователей с одобрением администратора

## Приоритет
high (закрывает уязвимость H2 аудита: сейчас любой пользователь Telegram может
скачать всю библиотеку; если бот уже доступен публично — считать blocker)

## Проблема
В боте полностью отсутствует авторизация: любой пользователь Telegram, знающий
username бота, может выполнить `/start`, `/author`, `/title`, `/get N` и скачать
все книги оператора. Личная библиотека не имеет порога доступа.

## Цель
Доступ к поиску и скачиванию книг получают только пользователи, явно одобренные
единственным администратором, через поток регистрации с ручным одобрением заявок.

## Пользователи
- **Администратор** — единственная учётная запись, задаётся через переменную
  окружения (Telegram ID). Автоматически имеет доступ; управляет заявками.
- **Пользователь** — любой, кто написал боту; до одобрения доступа к библиотеке не имеет.

## Сценарий использования
### Регистрация и одобрение
1. Неизвестный пользователь пишет боту → видит сообщение об ошибке (доступ закрыт)
   и кнопку «Зарегистрироваться».
2. Нажимает «Зарегистрироваться» → заявка уходит администратору: Telegram ID,
   имя, фамилия, @username, язык клиента + кнопки «Принять» и «Отклонить».
3. Пользователь в статусе «ожидает одобрения» получает статусное сообщение;
   команды поиска ему недоступны; повторные нажатия не создают дубли заявок.
4. Администратор нажимает «Принять» → пользователю отправляется уведомление об
   одобрении, открывается библиотека; сценарий использования бота одобренным
   пользователем не меняется.

### Отклонение
5. Администратор нажимает «Отклонить» → пользователю отправляется уведомление об
   отказе; пользователь попадает в blacklist: новые заявки отправить не может,
   доступ к библиотеке закрыт.

## Функциональные требования
- FR1. Неодобренные пользователи (нет заявки / ожидает / в blacklist) не получают
  результатов поиска и файлов — только сообщения своего статуса.
- FR2. Каждый новый пользователь может отправить ровно одну активную заявку.
- FR3. Заявка содержит идентификатор Telegram, имя, фамилию, @username, язык клиента.
- FR4. Решение администратора принимается только двумя кнопками на сообщении заявки.
- FR5. Одобренные и отклонённые (blacklist) пользователи хранятся в БД и переживают
  перезапуск бота.
- FR6. Наличие/статус пользователя определяется по Telegram ID из БД на каждом запросе.
- FR7. Переменная окружения с Telegram ID администратора обязательна: без неё бот
  не стартует (fail-fast, как другие обязательные переменные).
- FR8. Пользователь получает уведомление о результате решения администратора
  (одобрен / отклонён).
- FR9. Все новые пользовательские строки и надписи кнопок — на английском языке
  (консистентность с существующими строками бота).

## Критерии приёмки
- [x] Без заданного ID администратора бот не запускается с внятным сообщением.
- [x] Незарегистрированный пользователь не может получить данные библиотеки.
- [x] «Зарегистрироваться» → администратор получает заявку со всеми полями и двумя кнопками.
- [x] Из pending нельзя создать дубль заявки и пользоваться поиском.
- [x] «Принять» → пользователю доступны /start, /author, /title, /result, /get как раньше.
- [x] «Отклонить» → пользователь в blacklist: ни доступа, ни повторной заявки.
- [x] После «Принять»/«Отклонить» пользователю приходит уведомление о результате.
- [x] Все новые строки и подписи кнопок — на английском.
- [x] Статусы (одобрен/отклонён) сохраняются после перезапуска бота.
- [x] `go vet ./...` и `go test ./...` проходят.

## Edge cases
- Нажатие кнопок на уже обработанной/устаревшей заявке — решение повторно не меняется,
  администратор получает понятный ответ.
- Отсутствующие у пользователя фамилия/@username — в заявке показывается только то, что отдал Telegram.
- Заявка/повторное обращение от blacklist-пользователя — только отказ, без новой заявки.
- Сам администратор не проходит регистрацию и не может попасть в blacklist.
- Поток рассчитан на личные сообщения; сообщения в группах бот игнорирует
  (явное допущение — при публичном боте это единственная безопасная интерпретация).
- Повторное «Принять» для уже одобренного — идемпотентно.

## Не в рамках задачи
- Отзыв доступа у одобренного, разбан blacklist, просмотр списков, роли, несколько админов.

## Зависимости
- Хранение состояний пользователей в существующей БД (схема — за архитектором).
- Обработка нажатий кнопок (callback) в Telegram: транспортно требует приёма
  не-`message` обновлений, что пересекается с находкой аудита H1 (падение бота на них) —
  архитектор должен учесть это явно.
- Новая обязательная переменная окружения (Telegram ID администратора); обновить `.env.example`.
