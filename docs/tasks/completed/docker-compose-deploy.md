# Подготовка проекта к деплою через Docker Compose

## Приоритет
high

## Проблема

Проект нельзя развернуть в проде без ручной работы на хосте: нет Dockerfile, нет
docker-compose, нет шаблона окружения, нет скриптов запуска. Сейчас пайплайн
(`scan` → `db-create` → `bot`) запускается вручную бинарями, собранными локально,
логи пишутся прямо в файлы (`log.log`, `scan-books.log`), а переменные окружения
читаются напрямую из окружения процесса без какого-либо файла конфигурации.

Дополнительно мешают:
- баги в `cmd/bot/main.go:34` — `slog.Error("failed to init storage", err)` с
  голым `err` как аргументом ломает `go vet ./...` и `go test ./...`
  (`cmd/bot [build failed]`), из-за чего невозможно проверить сборку;
- имена переменных окружения вводят в заблуждение: `DB_PATH` — это на самом деле
  каталог с `.zip`-архивами, а не путь к базе;
- в репозитории закоммичены артефакты данных и сборки (`db.sqlite3` размером
  ~324 МБ, бинарь `db-create`), которые в проде должны приходить из
  монтируемых каталогов, а не из репозитория.

## Цель

Проект разворачивается в проде по инструкции из README: оператор копирует
`.env.example` в `.env`, заполняет значения, выполняет `./build.sh` и `./up.sh`,
после чего бот работает. Пополнение библиотеки и пересборка базы выполняются
разовыми запусками контейнеров через `./scan.sh` и `./db-create.sh`. Все логи
идут в stdout, файлы приложения на диске не создаются.

## Пользователи

- Оператор деплоя/администратор сервера: копирует `.env.example`, правит значения,
  запускает скрипты.
- Владелец библиотеки: пополняет каталог с `.zip`-архивами, запускает `./scan.sh`
  и `./db-create.sh` для переиндексации.

## Сценарий использования

### Первичный запуск в проде
1. Оператор создаёт на хосте каталоги, указанные в `.env` (каталог с `.zip`-архивами
   и каталог под базу данных). Создание каталогов — ручная операция, порядок описан
   в README.
2. Оператор кладёт `.zip`-архивы с книгами в каталог библиотеки.
3. Оператор копирует `.env.example` в `.env` и заполняет значения: токен Telegram-бота,
   пути к каталогам на хосте, прочие параметры.
4. Оператор выполняет `./build.sh` — собираются образы всех трёх сервисов.
5. Оператор выполняет `./up.sh` — запускается бот.
6. Оператор в Telegram отправляет боту `/start`, получает ответ, ищет книгу по
   автору/названию, скачивает её — бот отдаёт файл из архива.

### Пополнение библиотеки
1. Оператор добавляет новые `.zip`-архивы в каталог библиотеки на хосте.
2. Оператор выполняет `./scan.sh` — контейнер разово отрабатывает, разбирает архивы,
   пишет рядом с ними `.zip.json`-sidecar-файлы и пишет логи в stdout.
3. Оператор выполняет `./db-create.sh` — контейнер разово отрабатывает, читает
   sidecar-файлы и наполняет базу.

### Повторный запуск после рестарта сервера
1. Оператор выполняет `./up.sh` (или `docker compose up -d`) — бот поднимается
   на уже существующих данных без пересборки и переиндексации.

## Функциональные требования

### FR1. Контейнеризация
- Все три бинаря (`bot`, `scan`, `db-create`) собираются в Docker-образы.
- Сборка должна учитывать требование cgo (`github.com/mattn/go-sqlite3`):
  `CGO_ENABLED=1` и C-тулчейн внутри образа.
- Секреты и конфигурация не запекаются в образ — всё приходит через переменные
  окружения.

### FR2. Единый docker-compose
- Один compose-файл описывает все три сервиса.
- `docker compose up -d` поднимает **только** бот.
- `scan` и `db-create` присутствуют в compose как сервисы, но не стартуют при
  `up -d` — они запускаются разово по требованию (например, через профиль,
  который не активен по умолчанию, либо через `docker compose run`).

### FR3. Файл `.env.example`
- В репозитории лежит `.env.example` с полным перечнем переменных и
  комментариями-подсказками по назначению каждой.
- Оператор копирует его в `.env` (`.env` в `.gitignore`) и правит значения.
- Все значения подставляются в compose-файл через синтаксис `${ПЕРЕМЕННАЯ}`.
- Пути к монтируемым каталогам задаются в `.env` как переменные, а не зашиты
  в compose-файл.
- Значения по умолчанию в `.env.example` должны быть рабочими для типового
  окружения (например, относительные пути под каталог `data/`).

### FR4. Переменные окружения
- Имена переменных окружения в коде приведены в порядок:
  - каталог с `.zip`-архивами — понятное имя (например `LIBRARY_PATH`)
    вместо нынешнего `DB_PATH`, который вводит в заблуждение;
  - строка подключения к SQLite — понятное имя (например `DB_DSN`).
- Токен бота и опциональный `HTTP_PROXY` продолжают читаться из окружения.
- Отсутствие обязательной переменной должно давать понятную ошибку в логах и
  корректное завершение процесса (ненулевой код возврата), а не тихий `return`.
- Если новое имя выбрано с расчётом на совместимость со старым — старый вариант
  поддерживается как фолбэк; если совместимость не нужна — старое имя удаляется
  и все упоминания (код, документация, скрипты) обновляются единообразно.

### FR5. Скрипты
- `./build.sh` — собирает образы **всех** трёх сервисов (включая `scan`
  и `db-create`), чтобы они были готовы заранее.
- `./up.sh` — выполняет только `docker compose up -d`.
- `./scan.sh` — разово запускает контейнер `scan` с корректными аргументами
  (каталог библиотеки) и завершается с кодом возврата контейнера.
- `./db-create.sh` — разово запускает контейнер `db-create` с корректными
  аргументами (каталог с sidecar-файлами и путь/DSN базы).
- Скрипты не должны требовать ручной установки чего-либо на хост и не должны
  собирать бинарии Go на хосте.
- Скрипты запускаются из корня репозитория и не требуют ручной установки
  переменных окружения — они читают `.env` сами (через compose).

### FR6. Логи и файлы
- Ни один компонент не пишет файлы логов напрямую (`log.log`,
  `scan-books.log` не должны появляться в рабочем каталоге контейнера).
- Все сообщения идут в stdout/stderr в структурированном виде и видны через
  `docker compose logs`.

### FR7. Монтируемые каталоги
- Каталог с `.zip`-архивами монтируется в контейнер бота (только чтение
  достаточно) и в контейнер `scan` (нужен режим чтения/записи, потому что
  `scan` создаёт рядом с архивами `.zip.json`-sidecar-файлы).
- База данных SQLite монтируется в контейнеры `bot` и `db-create`; путь внутри
  контейнера и путь на хосте задаются через `.env`.
- Создание каталогов на хосте — ручная операция, порядок и требования описаны
  в README.

### FR8. Гигиена репозитория
- Из отслеживаемых git файлов убираются артефакты данных и сборки:
  `db.sqlite3`, бинарь `db-create`, файлы логов (`*.log`), `.env`.
- `.gitignore` дополнен отсутствующими правилами.
- Перед удалением из индекса должно быть подтверждено, что данные не теряются
  (достаточно, чтобы они были воспроизводимы сканированием библиотеки).

### FR9. README
- В репозитории появляется README с инструкцией по развёртыванию:
  - требования (Docker, Docker Compose);
  - порядок первичного развёртывания: создание каталогов → копирование
    `.env.example` в `.env` → заполнение значений → `./build.sh` → `./up.sh`;
  - описание каждой переменной `.env`;
  - описание скриптов `build.sh`, `up.sh`, `scan.sh`, `db-create.sh`;
  - **явное предупреждение**, что `scan` монтирует каталог библиотеки в режиме
    чтения/записи и изменяет содержимое этого каталога на хосте (создаёт
    `.zip.json`-файлы рядом с архивами), поэтому права и владелец каталога
    на хосте будут затронуты;
  - описание поведения при повторном запуске `db-create` (дублирование строк,
    так как у вставки нет уникального ограничения и upsert-а) и какой порядок
    действий использовать для переиндексации;
  - команды диагностики: `docker compose ps`, `docker compose logs`,
    ручная проверка бота через `/start` в Telegram.

## Варианты использования

### UC1. Первичное развёртывание
Оператор создаёт каталоги, копирует `.env.example` в `.env`, заполняет токен и
пути, выполняет `./build.sh`, затем `./up.sh`, проверяет `docker compose ps` и
отправляет боту `/start` — бот отвечает. Каталог данных при этом на хосте
создаётся руками, ничего не падает из-за отсутствующих путей.

### UC2. Пополнение библиотеки
Оператор добавляет `.zip` в каталог, выполняет `./scan.sh` (логи в stdout),
затем `./db-create.sh`. После этого новая книга находится ботом и скачивается.

### UC3. Развёртывание, когда каталог данных уже существует
Оператор выполняет только `./build.sh` и `./up.sh` — данные не перезаписываются,
бот поднимается на существующей базе. Никакой переиндексации не происходит.

### UC4. Развёртывание с прокси
В `.env` задан `HTTP_PROXY` — бот работает через прокси; если переменная не
задана, бот работает напрямую.

### UC5. Ошибка конфигурации
Оператор забыл заполнить обязательную переменную (например, токен бота) или
указал несуществующий путь. Ошибка видна в логах контейнера с понятным
сообщением, контейнер завершается с ненулевым кодом, бот не стартует молча.

### UC6. Ручная проверка после деплоя
Оператор выполняет `docker compose ps` (контейнер бота в состоянии `Up`),
`docker compose logs bot` (видны сообщения о запуске), отправляет боту `/start`
и получает ответ, выполняет поиск по автору и скачивает книгу.

## Критерии приёмки

- [ ] В репозитории есть Dockerfile (или эквивалентная логика сборки),
      собирающий `bot`, `scan` и `db-create` с работающей поддержкой cgo
- [ ] `docker compose build` собирает образы всех трёх сервисов
- [ ] `./build.sh` выполняет сборку всех трёх сервисов и завершается с кодом 0
- [ ] `./up.sh` выполняет `docker compose up -d` и поднимает только бот
- [ ] `docker compose ps` после `./up.sh` показывает запущенный контейнер бота
      и не показывает запущенными `scan` и `db-create`
- [ ] `./scan.sh` разово запускает контейнер `scan`, отрабатывает до завершения
      и возвращает код возврата контейнера
- [ ] `./db-create.sh` разово запускает контейнер `db-create` и возвращает код
      возврата контейнера
- [ ] В репозитории есть `.env.example` со всеми переменными и комментариями
- [ ] Все значения переменных подставляются в compose-файл через `${ПЕРЕМЕННАЯ}`,
      пути к монтируемым каталогам в том числе
- [ ] `.env` остаётся в `.gitignore`
- [ ] Переменная каталога с архивами переименована из `DB_PATH` в понятное имя,
      переменная подключения к SQLite переименована из `DB_CONNECTION_STRING`
      в понятное имя; все упоминания в коде, compose-файле, скриптах и README
      обновлены согласованно
- [ ] Каталог архивов монтируется в `scan` с правами на запись, в `bot` —
      минимум на чтение
- [ ] Путь к базе данных монтируется в `bot` и `db-create`
- [ ] В рабочем каталоге контейнеров не появляются `log.log`,
      `scan-books.log` и любые другие файлы логов; логи видны в stdout
- [ ] Отсутствие обязательной переменной приводит к понятному сообщению в логах
      и ненулевому коду возврата
- [ ] `go build ./...` проходит успешно
- [ ] `go vet ./...` и `go test ./...` не падают на `cmd/bot` из-за бага
      `slog.Error` с голым аргументом `err`
- [ ] Файлы `db.sqlite3`, бинарь `db-create`, `*.log` и `.env` не отслеживаются
      в git; `.gitignore` дополнен
- [ ] В репозитории есть README с описанным выше порядком первичного
      развёртывания, описанием переменных и скриптов, предупреждением о
      записи в каталог библиотеки, предупреждением о дублировании строк при
      повторном `db-create` и командами диагностики

## Edge cases

- Каталог библиотеки или каталог базы не создан на хосте → compose может
  не стартовать или приложение падает с ошибкой; должно быть понятное сообщение,
  а README должен описывать шаг создания каталогов вручную.
- `scan` требует прав записи в каталог библиотеки на хосте. Если каталог
  принадлежит другому пользователю, `scan` упадёт с ошибкой прав доступа —
  это ожидаемое поведение, отражённое в README.
- Частично обработанная библиотека: `scan` логирует ошибки по отдельным архивам
  и пропускает их, а не падает целиком. Пропущенные архивы должны быть видны
  в логах stdout.
- Повторный запуск `db-create` без очистки базы дублирует строки (вставка без
  уникального ограничения и upsert-а). Это нужно явно описать в README как
  известное ограничение с рекомендуемым порядком действий.
- Библиотека изменилась после первой индексации → оператору нужен понятный путь
  переиндексации, описанный в README.
- Оператор не переименовал старые имена переменных (`DB_PATH`,
  `DB_CONNECTION_STRING`) — поведение должно быть предсказуемым: либо
  поддержан фолбэк, либо будет чёткая ошибка о неизвестной конфигурации, а не
  молчаливое использование неверного пути.
- Пустое значение `BOT_TOKEN` или `DB_DSN` → процесс завершается с ненулевым
  кодом, в логах видно, какая переменная не задана.
- `HTTP_PROXY` не задан → бот работает напрямую; переменная пустая — не должна
  превращаться в невалидный прокси-адрес.
- Архивы, которые не удалось распаковать или распарсить, не должны приводить к
  падению всего `scan`; ошибки видны в логах.

## Нефункциональные требования

- Образы должны быть минимально разумными по размеру (многоступенчатая сборка:
  сборка Go в отдельном слое, в финальный образ только бинарь и необходимые
  системные библиотеки).
- Сборка должна работать с включённым cgo; `go build ./...` должен проходить
  локально без падений.
- Обеспечена корректная остановка бота по `SIGTERM` (graceful shutdown) —
  контейнер должен завершаться без потери состояния, а падать в restart-loop
  не должен.
- Скрипты и README должны работать на типовом Linux-хосте с установленными
  Docker и Docker Compose; дополнительные зависимости не требуются.
- Секреты (токен бота) не попадают в образы, в git и в вывод `docker inspect`
  сверх необходимого (передаются через переменные окружения из `.env`).
- Никаких изменений в бизнес-логике поиска, скачивания и сканирования.

## Решения заказчика

- Один compose-файл на все три бинаря.
- `scan` и `db-create` не поднимаются при `docker compose up -d`; они запускаются
  разово через `./scan.sh` и `./db-create.sh`.
- `build.sh` собирает все три сервиса, `up.sh` выполняет только `up -d`.
- Переменные окружения переименовываются в понятные; совместимость со старыми
  именами — на усмотрение реализации, но поведение при старых именах должно быть
  предсказуемым.
- Логи — только в stdout, файлы логов приложением не создаются.
- Каталоги данных на хосте создаются вручную; порядок описывается в README.
- Приёмка — ручная проверка оператором; автотесты для деплоя не требуются,
  но существующие тесты и `go vet`/`go build` должны проходить.
- В репозитории появляется README, хотя сейчас единственным документом является
  `AGENTS.md`.

## Зависимости

- Docker Engine и Docker Compose (Compose v2) на целевом хосте.
- Существующий Telegram-бот и его токен.
- Заранее подготовленный каталог с `.zip`-архивами книг на хосте.
